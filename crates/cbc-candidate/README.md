# CBC candidate local core

This package is an isolated local development target, not a replacement for installed CBC.
It provides a private local socket and a bound core API. Native adapters are experimental;
their evidence is separate from synthetic core tests. There is no installer or daily cutover.
It does not use legacy runtime modules, service labels or default database paths for storage.

The [native lifecycle and room policy](../../docs/design/cbc-agent-lifecycle-and-rooms.md)
records environment-aware creation/messaging and uncapped rooms with informational milestones.
Saved native environment selection is distinct from cwd and UI grouping. The candidate has
no lifetime message cap. Informational notices count distinct committed participant sends,
notify only the report parent or both peers, and require no extension vote or response.
Complete native creation remains separate acceptance work. See [EVIDENCE.md](EVIDENCE.md)
for actual native delivery results, including the in-process Claude mod path. The channel-only
Desktop activation gate is separate from that tested mod transport.

Build and test only this package with one job and separate artifacts:

```sh
rtk cargo test -p cbc-candidate --target-dir target-candidate -j 1 --offline -- --test-threads=1
```

The executable provides `init`, read-only `inspect`, `serve`, owner `provision`, expected-epoch
`revoke`, and live `settings` commands. All require an explicit absolute
`--root` and an additional absolute `--protected-db` identifying the daily database. Init
also requires `--port`; it records that value but does not bind a listener. Init never adopts
an existing directory. There is no candidate `--db` override or legacy environment fallback.

`serve` opens the candidate store and listens only on `<root>/connector.sock`, never TCP.
It uses one current-thread Tokio runtime plus SQLite's worker. SIGINT/SIGTERM drain the core;
no per-room process or timer is created. Socket paths must be shorter than 104 bytes.

Production protection always includes environment-home and OS-account-home `.chatbotchat`
directories, plus the explicit protected path and legacy `CBC_DB`. Port 8484 and ports from
legacy `CBC_PORT`/`CBC_SERVER` are protected regardless of host spelling. Legacy settings only
add restrictions; they never select candidate storage or cause a connection. Relative or
malformed legacy settings fail closed. Protection may read filesystem metadata for daily
paths, but never opens them through SQLite or contacts the daily endpoint.

`Sandbox` checks private ownership/modes, manifest namespace/root/version/size, canonical
directory overlap and file identities, and rejects linked/foreign database files and SQLite
sidecars before a store can open. `candidate.sqlite3` is fixed beneath the candidate root.
These checks do not protect against malicious concurrent code running as the same OS user.
The first implementation targets Unix systems such as macOS and Linux.

The library's `Store` is a trusted synthetic-fixture API. It stores contexts and members,
using a versioned candidate-only SQLite schema and one connection. It is NOT public
agent enrollment. A cooperative OS lease prevents two open cores; callers must await
`close()` before intentionally releasing ownership. An accidental drop retains the lease while
a short-lived cleanup thread awaits pool shutdown. Failure to establish shutdown retains the
lease until process exit; it cannot silently hand an open database to a second core.

Bootstrap builds a branded database privately with DELETE journaling and publishes it only
after migration. Normal candidate operation then uses WAL. An interrupted bootstrap with a
leftover staging file fails closed and requires a fresh disposable root; no automatic recovery
or deletion of that file is claimed. Existing durable contexts are never copied from daily CBC.
SQLx migration history/checksums own schema compatibility. The header is an early future-format
check; validated migration history derives its version, so older/checkpoint-lagging headers can
be reconciled. Migration 0002 adds context-scoped members and binding epochs. Its upgrade test
uses a preserved database generated by the actual v1 build, not a new current-schema database.
Migration 0003 preserves an actual v2 fixture, adds Domain Lead, and creates the inbox tables.
Migration 0004 preserves an actual v3 fixture and adds enrollment invitations, directory
metadata and scoped connection grants. Domain Lead remains a historical compatibility role.

## Member and session binding

Registration fixes a logical member's role within its context. Identical registration preserves
its binding; a different role conflicts. The role is a classification, not a full capability grant.
Binding attaches a device/native-session identity and returns a random 256-bit credential once.
Only its SHA-256 digest is stored. Debug and Display redact credentials; the credential type
is not serializable. Explicit token access is for a trusted host adapter, never model output.
Parsing a token's accompanying claims does not authorize them. `current_member` validates the
digest in constant time and checks context/member, device, native session and current epoch.
It is a snapshot, not a reusable authorization result. Future actions must validate within
their own database transaction, including when committing a state patch or delivery event.

Every bind, including a retry, rotates the credential and increments the epoch. Only the latest
binding remains current. Unbind increments the epoch and revokes the session but keeps the
member registered. Remove also disables the member and revokes its room grants, refusing bind
until trusted registration reactivates it. Registration does not restore old room access.
Neither operation deletes the member's epoch history. The last epoch value is
reserved for revocation, so even the last issued credential remains revocable. Exhausted
members cannot bind again; registration cannot reset their counter. Repeated unbind of an
active member also increments the epoch; repeated removal of an
inactive member is rejected. Re-registration never changes its role or restores an old credential.

These low-level methods are trusted administration only. They do not prove native-app identity
or authenticate HTTP requests. A stale native
tool already executing is not cancelled by fencing later CBC operations.

## Owner enrollment and connections

The running core creates a private `owner.key`. Owner commands use that key through the same
socket and Store, rather than opening a second database owner. `provision` requires a manifest
of freshly verified native sessions and writes a new mode-0600 device profile inside the
candidate root. It never prints credentials. The operator must corroborate actual host IDs
first; an `evidence_ref` string alone is not evidence. Setup is fresh-member-only and may be
partial after a failure, so an uncertain result must not be blindly retried.

Enrollment invitations are short-lived, single-use and stored by digest. They bind the
expected host, device, native session and member epoch. Bound agents can discover only
authorized connections and establish report or peer rooms through `cbc_discover` and
`cbc_connect`. Report routes connect Chapter Masters and Primarchs. Peer routes connect
members at the same working tier. Creation records membership and a structured introduction
atomically; identical retries reuse the existing connection. Ordinary report introductions
are deterministic. Peer introductions can add a bounded explanation.

`settings` reads the current nonsecret policy or applies a revision-checked update without
restarting the core. Private JSON files hold defaults and context, role and member overrides.
Invalid updates retain the last accepted policy. Agents receive only their effective policy.
The device driver refreshes retry timing on actual failures, with no idle configuration poll.
The setup and isolated native acceptance procedure are in [TESTING.md](TESTING.md).
`revoke` fences exactly the expected current native binding, preserving logical membership
and unread history. A stale request fails without revoking a newer binding. It does not stop
an already-running native tool or change that host's permissions.

## Durable inbox and local socket

Rooms have explicit member grants and no lifetime message-count cap. Trusted fixture creation
accepts 2–128 distinct registered members; this input bound is not a conversation budget.
Repeating creation cannot change participants or restore revoked grants. The role field is not
yet a full hierarchy capability policy. Only trusted owner setup can authorize connections.

Send, check, receipt and close validate the current credential/epoch inside `BEGIN IMMEDIATE`.
Sends are idempotent by context/member/key; changed room or body conflicts. Messages are rows
with globally unique server sequences. Closure appends a final item and preserves earlier
unread messages. A pre-close successful send can still be retried after close.

Checks exclude the sender and rotate fairly across rooms with a persisted cursor. New batches
target at most 32 items and 48 KiB of serialized item JSON. Existing pending batches remain
immutable up to the 128 KiB compatibility ceiling; an older unread item exceeding the new
target can drain intact on its own. Bodies are limited to 16 KiB of UTF-8 and 32 KiB once
JSON-escaped, excluding the two quote delimiters. Ordinary ANSI/control text can pass.
Checks persist one immutable pending batch per member/epoch; checks and restarts replay it
until the trusted adapter receipts that exact batch. Receipts are idempotent and acknowledge
only those items, never comprehension or completion. Rebind supersedes pending references and
reoffers unread items. Membership removal cancels mixed batches without returning revoked data.

The version-1 local protocol is one bounded JSON line per connection:

```text
{v:1, auth:{context,member,device,session,epoch,token}, request:{op,...}}
```

Member operations are `check`, `send` (room/key/body), `receipt` (reference), `close` (room),
`watch` and `watch_members` (others/after), `binding_status`, `settings`, `discover` and `connect`.
Replies have `type`: `empty`, `batch` (items/reference), `sent` (sequence), `receipted`, `closed`
(sequence), `changed` (sequence), or `error`. The token and batch reference belong only to trusted transport code;
neither is model output. `LocalClient::check()` takes no IDs or room arguments. Empty success
is distinct from unavailable transport or rejected authorization.

`watch_members` is an additive targeted feed. Its `members_changed` reply contains a sequence
and at most 64 `{context, member, sequence}` hints, only for subscribed members with eligible
unread data after the requested sequence. It returns no bodies, credentials or receipt tokens,
creates no pending batches and receipts nothing. The older sequence-only `watch` remains compatible.
All subscribed bindings are validated in the same read transaction before any hint is returned.

One router watches all its registered bindings through one connection. The outer auth is the
first binding; `others` contains the rest, up to 64 distinct context/member pairs total.
`after` is a nonnegative server sequence. All bindings must be current. The feed waits without
an idle timer until an authorized, unreceipted, non-self item has a higher sequence. It emits
only that sequence, creates no pending batch and acknowledges nothing. Every successful writer
signals the same feed. Subscribe-before-query and the durable message query recover a commit
whose in-memory wake was lost. Reconnecting at zero recovers unread messages after restart.
Disconnected watchers release their connection slot. Actual failures can back off; an empty
inbox does not cause periodic requests or model turns.

`adapters/shared/feed.py` supplies host-neutral dispatch inside the device router. One parked
connection covers the registered members and invokes only the changed members' registered
host callbacks. It validates the entire hint before dispatch, keeps context/member keys distinct,
uses a fixed two-worker delivery budget, and coalesces pending hints per member. A false/failed
callback remains queued with 1–30 second failure backoff, without waiting for another message;
other members continue. Successful idle operation has no retry deadline. Callbacks return True
or None on acceptance and False on temporary unavailability, and must bound native calls.
Stop does not cancel an external action already running. Reconnect starts at zero to recover
unread work; explicit stop interrupts the parked connection. No hint marks messages receipted,
handled, or approved. Pending hints are recoverable from the durable unread inbox after restart.

The [shared device driver](adapters/device/README.md) uses one feed for both hosts. Claude
uses a corroborated live session and an opt-in MCP channel through its stdio shim, with one
shared selector for subscriptions. Codex uses a bounded invocation of the installed
`codex queue` command to deliver a content-free hint. Queue acceptance is not native receipt
or proof that a dormant chat woke. Required host MCP stdio shims still count as processes;
there are no per-room polling shells. The integration tests route to synthetic callbacks
against the actual candidate store and socket, not native apps. Run feed tests separately:

```sh
rtk proxy python3 -I crates/cbc-candidate/adapters/shared/test_feed.py -v
```

Native integration status as of 2026-11-04: the current shared driver has process-level
tests, not a real-app PASS. Claude channels require native preview enablement and consent.
The public Codex controller socket was absent in an earlier read-only check; no daemon was
started and no private Desktop endpoint was substituted. Current native queue/channel
uptake, active/idle delivery and reconnect must pass in both apps before closing #113.

The socket lives inside the private candidate root with mode 0600, checks peer UID, refuses
existing paths, limits frames/connections/request time and removes only its own inode on shutdown.
Parked watch requests have no idle deadline. Transient accept errors retry with bounded backoff;
an owned child-only descriptor-exhaustion test verifies recovery without changing host limits.
This is a same-OS-user boundary, not protection from malicious code running as that user.
There are no anonymous admin routes and no HTTP listener. A native router must corroborate
the caller before selecting the binding; merely presenting a native session ID is insufficient.

`examples/seed_native_fixture.rs` is trusted disposable setup, not enrollment. It accepts a
fresh candidate root, an explicit nonsecret specification file, and the protected daily DB
path. The specification has context/device/room and members with member/session fields. It
binds each fixture member once, writes `native-bindings.json` exclusively at mode 0600, and
prints only the profile path and room. The secret profile is adapter input, never chat material.
A failed fixture setup may be partial; use a fresh disposable root rather than retrying it.

## Required redesign capabilities still to build

Internal/outward JSON maps,
separately owned Primarch notes, questions, controls, shared dashboard projections and durable
deadline/checkpoint attention are required parts of this redesign. They are successive tested
slices, not optional plugins. The shared context/member identity and epoch are their ownership
basis. Expected-revision checks and atomic state-plus-notification commits must accompany
their implementation. One core will own scheduling; no per-agent timers or empty AI ticks.
The active working hierarchy is Primarch to implementation-owning Chapter Master. Historical
Domain Lead/Task Agent classifications remain readable for compatibility; they do not require
extra coordination tiers. The future Emperor reads dashboard data and is outside reporting;
no current connector route should depend on an Emperor report or approval.
Connector/native delivery in both Codex and Claude remains required before real-agent adoption.
No native-app PASS is implied by core or socket tests. Both native profiles and dormant-chat
wake/recovery remain acceptance gates. In particular, a Claude Desktop session socket vanishes
when the app terminates its idle process; live socket delivery does not establish dormant wake.
